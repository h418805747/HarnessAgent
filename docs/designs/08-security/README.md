# 08 Security 安全

> 状态：草案 v0.2（依据"安全不可被 Agent 卸载"评审修订）
> 对应概要设计 §2.3、§5.4

## 0. 定位：信任根，而非普通插件

上一版把 Security 简单列为"可替换插件"，存在严重缺陷。必须区分三个被混为一谈的概念：

| 概念 | 含义 | Security 是否适用 |
|---|---|---|
| **可替换 Replaceable** | 实现可换，接口保持不变 | ✅ 是（策略引擎 / 沙箱后端 / 密钥后端可换） |
| **可卸载 Removable** | 运行期可整体移除且系统仍能工作 | ❌ 否（移除即等于关闭安全） |
| **可被 Agent 卸载 Agent-removable** | 模型可通过工具调用触发移除 | ❌ **绝对禁止** |

**结论：Security 是内核信任根（TCB）常驻组件。它可以"被换实现"，不可以"缺席"，更不可以"由 Agent 触发移除"。**

> "Everything is a plugin" 适用于**能力（capability）**，不适用于**信任根（trust root）**。
> 类比操作系统：内核调度器、安全模块不能被用户态进程卸载；但防火墙实现可以由 root 在**启动时**替换。

## 1. 威胁模型

| 编号 | 威胁 | 场景 |
|---|---|---|
| T1 | **提示注入卸载安全** | 网页/文件/工具输出等外部内容诱导模型调用"卸载插件""关闭安全" |
| T2 | **策略篡改** | 模型或第三方插件修改安全策略、白名单、`always-allow` 记录 |
| T3 | **审批伪造/绕过** | 绕过审批链直接执行敏感操作 |
| T4 | **密钥窃取** | 通过工具读取 `.env`、环境变量、凭证 |
| T5 | **审计破坏** | 删除/篡改审计记录以掩盖行为 |
| T6 | **插件投毒** | 恶意插件在挂载时注册高权限能力或覆盖安全组件 |

T1 是本模块设计的核心驱动威胁。

## 2. 分层结构（三层，权限递减）

```
┌── L1 Security Core（内核 TCB：常驻、不可卸载、不暴露为工具）──────────────┐
│  Policy Decision Point (PDP)      │  Policy Enforcement Point (PEP)      │
│  插件生命周期授权 Gate             │  配置变更授权 Gate                    │
│  保护清单 Protected Set 校验       │  审计锚点（append-only）              │
│  任何异常/超时 → fail-closed       │                                       │
└────────────────────────────────────┬──────────────────────────────────────┘
                                     │ 只通过接口调用（单向依赖）
┌── L2 Security Providers（插件：可替换，但不可缺）─────────────────────────┐
│  策略引擎 IPolicyEngine │ 沙箱后端 │ 密钥后端 ISecretStore │ 审计 Sink │ 检测器 │
│  规则：缺失/加载失败 → 拒绝；绝不 → 放行（fail-closed）                    │
└────────────────────────────────────┬──────────────────────────────────────┘
┌── L3 Admin Operations（带外，需人类显式授权）─────────────────────────────┐
│  修改策略 / 挂载卸载插件 / 关闭安全                                        │
│  仅控制面（CLI、配置文件、supervisor）可发起                               │
│  需人类确认 + 重启或监督模式；永不注册为模型可调用的工具                    │
└────────────────────────────────────────────────────────────────────────────┘
```

## 3. 关键设计点

### 3.1 控制面 / 数据面分离（最核心）
- **数据面**：模型运行于此，只能**请求**动作（工具调用）。
- **控制面**：插件挂载/卸载、策略修改、配置变更、密钥读写。
- **规则**：数据面**永远无法**驱动控制面。模型不能挂载/卸载任何插件，也不能修改安全策略。

### 3.2 结构性隔离优先于策略判定
- 最强防护是"**模型根本没有这个工具**"。
- 插件管理、安全开关、策略编辑、密钥管理**一律不注册为工具**，因此通过提示注入也无可调用之物。
- 策略判定（L1）只是第二道防线，不是唯一防线。

### 3.3 授权与执行分离
- 即便 Creator 模式需要插件管理能力，也必须：`ISecurityCore.authorize_control_plane()` 判定 + **人类审批** + 仅允许操作**非 TCB 插件** + 全程审计。
- 模型只能"请求"，人类才能"授权"。

### 3.4 TCB 冻结与保护清单
- bootstrap 完成后，**TCB 组件集合运行期不可变**；任何变更需重启。
- **保护清单（Protected Set）**：Kernel、Security Core、Plugin Host 权威、Config 权威、Audit。其 `protected=true`，卸载请求**直接拒绝**（不进入审批，直接 deny）。

### 3.5 Fail-closed
- 安全组件不可用、异常、超时、策略为空 → **一律拒绝**，绝不默认放行。
- Security 的"拒绝"决策**不依赖任何普通插件**（依赖循环是漏洞来源）。

### 3.6 风险分级与审批强度

| 风险级 | 示例 | 默认策略 |
|---|---|---|
| L0 只读 | 读文件、搜索 | 允许（可配置为记录） |
| L1 可逆写 | 写文件、创建目录 | 记录 + 可配置审批 |
| L2 破坏性/外发 | 删除、网络请求、执行命令 | 审批 |
| L3 控制面 | 挂载/卸载插件、改策略、改配置、读写密钥 | **强制人类审批，且不可 always-allow** |

**审批对象是"命令"，不是业务语义。** 读文件、写文件、删文件、执行 shell、网络请求，一律以**命令**形式提交，由**命令审核模块**（PEP + 规则库）判定 `allow / deny / ask`。任务、壳、IM 都不参与"什么该审批"的判定，只负责呈现与回传。

**规则库内容不在本文档定义**：上表是当前生效的基线，具体规则与提升条件（如覆盖已有文件是否加审）**后续单独讨论**，届时以规则库为准；在此之前严格按上表原样执行，任何文档不得自行增删规则。

### 3.7 always-allow 的边界
- 仅对 L0/L1/L2 生效，作用域受限（工具级 / 参数模式级 / 会话级）。
- **L3 永不可 always-allow**，每次都必须显式人类确认。

### 3.8 用户的自由（不牺牲安全）
- 用户是 root，**有权**关闭安全，但必须是：
  - **带外**：编辑配置文件 / CLI 显式操作；
  - **需重启**：不接受运行期热切换；
  - **有警告**：明确提示风险；
  - **留痕**：标记为 `unsafe mode` 并写入审计。
- 即"用户可以关，但不能在对话里被一句话关掉"。

### 3.9 审计与完整性
- 所有安全判定结果 append-only 写入事件流，可回放。
- 关键决策尽量 tamper-evident（哈希链，可选强度）。
- 插件清单校验；可选签名；标记来源可信度。

### 3.10 扩展与增强：在原生 Security 之上加力

**边界先说清**：能"叠加"的只有 L2；**L1 是权威，不能被普通插件包裹或改写**，只能整体换实现（属 L3：控制面授权 + 重启 + 审计）。TCB 的增强讨论统一收在本模块，不拆到 Runtime / Plugin。

| 增强方式 | 接法 | 约束 | 状态 |
|---|---|---|---|
| **替换 L2 实现**：策略引擎、沙箱后端、`ISecretStore`、审计 Sink | 实现接口 + manifest 声明，装配期注入 | 缺失 / 异常 → 拒绝（fail-closed）；L1 不依赖它也能拒绝 | 接口已定（§6） |
| **新增检测器**：注入检测、PII / 密钥泄露、内容合规、危险代码模式 | 注册为 L2 `IDetector`，挂到输入 / 输出 / 工具结果三个检测点 | 多个检测器的聚合规则需定义 | 待扩展为链 |
| **策略包（Policy Pack）**：不写代码，只加规则 | 规则库 / 配置，由策略引擎加载 | 规则库格式未定；当前按 §3.6 基线执行 | 待定 |
| **外部强制点**：独立 supervisor 进程、egress 代理、OS 级沙箱、WASM | 进程边界 + 协议 | 与"可跨机、不共享句柄"一致 | 列为待定（§8） |
| **审批流扩展**：Webhook / 外部审批系统 / 多人审批 | 替换 `IApproval` 实现或加审批后端 | L3 永不可 always-allow | 部分已定 |
| **审计增强**：哈希链、外部不可变存储、SIEM Sink | 替换审计 Sink | 审计 append-only，普通插件不可改写 | 强度待定 |

**硬规则：增强只能收紧，不能放宽。**

- user / project 级策略包只允许 **tighten**（加黑名单、提高风险级、扩大审批触发面）。
- 任何 **loosen**（关闭检测、降低风险级、新增 always-allow）必须走 L3：控制面 + 人类审批 + 审计 + 重启。
- 理由：`./.harness/` 与仓库一起分发，等同不可信输入；若它能放宽安全，就是一条注入式绕过路径。
- 增强 provider **不得覆盖** `authorize_control_plane()`、`is_protected()`、审计锚点这些 L1 权威。

**Provider SPI（建议）**：

```ts
interface ISecurityProvider {
  id: string;
  kind: "policy" | "detector" | "sandbox" | "secret" | "audit";
  scope: "input" | "output" | "tool_call" | "tool_result" | "mount" | "config" | "secret" | "egress";
  evaluate(ctx: ActionContext): Promise<Decision>;  // allow / deny / ask + risk + reason
  timeoutMs: number;
  failClosed: true;      // 超时 / 异常一律 deny
  canTightenOnly: true;  // 只能 deny 或提升风险，不能把 deny 改回 allow
}
```

**装配与失效语义（写死）**：

1. L1 按固定顺序调用 provider 链，聚合规则 **deny > ask > allow**。
2. 任一 provider 超时、抛错或未加载 → 该 scope 下 **deny**，绝不降级为放行。
3. provider 只在装配期注册，运行期不可变（TCB 冻结，§3.4）；新增安全插件需重启。
4. 第三方 provider 需签名 / 来源校验（§3.9、§8）。
5. L1 自身在没有 provider 时仍能独立做出"拒绝"，否则形成依赖绕过路径（§3.5）。

### 3.11 输出侧校验（Output Guard）

**定位与边界**

- **只检查输出文本内容**：公序良俗、法律法规、政治正确（按 profile / 租户策略可配）、有害内容、隐私与凭据泄露、版权片段、注入 / 越权痕迹。
- **动作安全不在这里**：工具调用、命令、URL、文件写入、网络目的地全部走 PEP `check(action)` → allow / ask / deny + 审批 + 沙箱（§3.6）。文本里"提到"一条命令不构成动作；只有它变成 `tool_call` 才进入动作路径。
- **这是合规层，不是安全边界**：内容检测是概率性的，必有漏检与误检，不能承担"阻止越权"的职责。真正的边界是控制面不暴露、PEP 拦截、沙箱与最小权限（§3.2 / §3.6）。
- 所有模型产出——thinking、正文、tool_call 参数、子代理输出、工具结果回显——都按**不可信输入**处理；调用点位于 Model Adapter 的流式出口与 Interface 渲染之间，以及 Session 落盘之前。

**三段式流程（推荐）**

```text
① Thinking（仅当 provider 暴露推理内容）
   流式过滤 + 脱敏 → 滚动检测凭据 / PII / 注入与越权信号
   凭据 / PII        → 该片段不展示，流程继续
   注入 / 越权信号   → 终止本次调用，丢弃该段，重试 ≤1
   内容合规问题      → 只记录信号，不中断（不面向用户，误判成本高）

② Answer（面向用户）
   积累到"可展示边界"→ 检测 → 放行；未通过则不放行
   未展示前命中      → 丢弃缓冲，带纠正提示重生成剩余内容，≤2 次
   已展示后命中      → 停止输出 + 安全提示；已展示部分尽量 replace / retract
   重试耗尽          → 替换为安全回复，终止本轮

③ Post-check（全文终审，可异步）
   对完整回答做一次全文复审：跨段拼接、语义、上下文意图
   发现问题 → replace / retract / 追加更正 + 审计
   终审只减少漏网，不能替代 ①②，也不是唯一防线
```

**"可展示边界"的粒度**

| 输出形态 | 放行边界 | 兜底上限 | 原因 |
|---|---|---|---|
| 普通叙述 | 句末标点（。！？；）或空行 | ~200 字符 / 1.5 s | 一句话才具备可判定语义；等太久影响体验 |
| 代码块 / JSON / YAML / XML | 结构闭合（``` 或配对括号） | 整块 | 半截内容可能看似无害，闭合后才暴露问题 |
| 命令 / URL / tool_call 参数 | 完整一条 / 完整对象 | 执行前 | 与 PEP 校验同粒度，防止"前段合法、后段危险" |
| 表格 / 列表 | 单行或单块 | 同行 | 按结构单位判定 |
| 无标点长流（日志、base64） | 定长滑窗 | 100–200 字符 | 兜底；宁可延迟，不可漏放 |

**检测器分层**

| 层 | 时机 | 检测内容 | 成本 |
|---|---|---|---|
| L0 规则 | 每个边界 | 凭据 / PII 正则、URL / 命令特征、已知违规词、注入模式 | 微秒级 |
| L1 轻量模型 | 每个边界（可采样） | 本地小模型分类：有害、违法、色情、暴力 | 毫秒级 |
| L2 强模型 / 外部服务 | 终审 | 语义级合规、跨段拼接、上下文意图 | 秒级；可异步，外发需符合隐私策略 |

**处置矩阵**

| 情形 | 处置 | 是否中断 |
|---|---|---|
| 凭据 / PII | 脱敏（掩码 / 替换）后展示；写审计；高敏级别告警 | 否 |
| 内容违规（未展示） | 丢弃缓冲 + 纠正提示重生成剩余；≤2 次后转安全回复 | 是（本次生成） |
| 内容违规（已展示） | 停止输出 + 安全提示；接口支持则 replace / retract；审计 | 是 |
| 注入 / 越权信号 | 终止本次调用、丢弃输出、重试 ≤1；反复出现则终止 Turn | 是 |
| 结构不合法（tool_call） | 不执行；错误回填给模型重试；超预算则终止本轮 | 是（该动作） |
| 动作相关 | 不在本流程；交 §3.6 PEP | — |
| 检测器超时 / 不可用 | 文本：暂缓放行并提示；动作：**fail-closed** 拒绝 | 是 / 降级 |

**为什么 thinking 不做内容合规重开**

- thinking 通常不面向用户，为措辞重开整次推理，成本高、收益低。
- thinking 阶段真正有价值的是**安全信号**：是否尝试绕过安全、外泄系统提示、诱导未授权能力。这类信号应终止，而不是重写。
- 部分 provider 不返回或只返回加密推理（内容不可读）。方案必须对"不可见"降级，不能假设一定可见。

> 思维链的产生位置、可见性形态与 Agent 边界，详见 [cot.md](./cot.md)。

**Interface 契约要求**

- `IStream.delta(text)` 增量推送；`IStream.retract(n)` / `Interface.replace(messageId, text)` 撤回或替换已展示内容。不支持撤回的通道（如部分 IM）退化为"停止 + 追加更正"。
- `ModelCapabilities.reasoningStream: "visible" | "opaque" | "none"`，Runtime 据此决定 thinking 阶段校验是否生效。
- 每次边界判定与处置写审计：命中类型、检测器、动作、耗时；不写原文整段。

**审计与存储取舍**：

- `model.response` 事件必须落盘（可回放）；若原文含密钥，存 **脱敏正文 + 原文哈希 + 判定结果**，原文进受控审计存储，不直接躺在事件流里。
- 每次判定（allow / deny / ask、脱敏动作）都是 append-only 审计事件。

**结构性提醒**：

- 控制面操作不注册为工具，模型即使在输出里"说服自己"也无可调用之物（§3.2）。
- 子代理输出、工具返回内容同样按不可信输入处理，不能只校验主模型的输出。
- 合规策略按 profile / 租户可配；默认策略是产品配置，不等同于法律意见。

## 4. 对提示注入的纵深防护

| 层面 | 措施 |
|---|---|
| 能力面 | 控制面操作不注册为工具（结构性，最强） |
| 授权面 | 即使请求抵达 L1，也被判定为"需人类授权" |
| 审批面 | L3 强制人类确认，不可 always-allow |
| 数据面 | 工具输出/外部内容标记为**不可信输入**，不得作为控制指令 |
| 完整性 | TCB 冻结 + 保护清单 + 变更需重启 |
| 检测面 | 注入检测器（可选），仅作纵深，不设为唯一防线 |
| 兜底 | Fail-closed + 审计告警 |

## 5. 范围

**做**：
- 权限策略模型、审批流、风险分级
- 控制面授权 Gate（插件生命周期、配置变更）
- 沙箱隔离策略、密钥管理、审计
- 输入/输出安全过滤（提示注入防护、脱敏）

**不做**：
- 不实现具体工具执行（提供判定，执行在 Tools）
- 不做企业级 RBAC/SSO（首版）

## 6. 对外接口（修订）

```text
# ---- L1 内核 TCB：常驻，不可卸载 ----
ISecurityCore
    check(action, ctx) -> Decision{allow|deny|ask, risk, reason}
    authorize_control_plane(op, ctx) -> Decision     # 仅控制面可调用；L3 强制人类
    is_protected(name) -> bool                       # 保护清单查询
IApproval
    request(action, ctx) -> Approval                 # L3 不可 always-allow
ISandboxPolicy
    resolve_backend(action, risk) -> ExecutionBackend
ISecretStore
    get(key) / set(key)                              # 独立于 config，不落事件流
IAudit
    record(decision, action, ctx) -> Event           # append-only

# ---- L2 可替换插件接口（内核只依赖接口，fail-closed）----
IPolicyEngine   # evaluate(action, ctx) -> Decision
IDetector       # inspect(content) -> Risk
```

**明确约束**：
- `unmount()` **不出现在任何安全接口上**；插件卸载走 `IPluginHost`，且**必须**先经 `ISecurityCore.authorize_control_plane()` + 人类审批。
- Security Core 的依赖方向是**单向向内**：它不依赖普通插件即可独立做出"拒绝"决策。

## 7. 依赖

- 内核（作为 TCB 常驻组件）
- Interface（审批交互 UI）
- Tools（隔离执行）

**禁止**：Security 不得依赖任何普通插件才能运行（否则形成绕过路径）。

## 8. 待定问题

- 保护清单是否允许用户扩展（例如保护自研插件）——倾向允许，但扩展操作本身是 L3。
- 审计 tamper-evident 的实现强度（哈希链 vs 外部不可变存储）。
- 是否需要独立"安全监督进程"（supervisor），与主进程隔离以防同进程内存篡改。
- `unsafe mode` 的边界定义与提示强度。
- 是否支持对 L3 操作的双人审批（当前为单用户场景，暂不需要）。
