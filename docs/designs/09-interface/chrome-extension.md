# Chrome 扩展形态（薄壳）设计备忘

> 状态：草案｜关联 `09-interface`、`08-security`、`05-tools`
> 背景：把"浏览器侧的 Agent 入口"做成 Chrome 扩展，Agent 本体可部署在本地或远端
> 结论：**扩展只做壳（权限代理 + 传输 + 页面能力），决策在 Agent；Agent 位置是部署选项，不是架构承诺**

---

## 1. 定位

| 扩展负责 | 扩展不负责 |
|---|---|
| 页面读写（DOM / 截图 / 网络） | 规划、推理、记忆 |
| 标签页发现与接管 | 任务状态机、调度 |
| 传输（把语义消息送给 Agent） | 决定"下一步做什么" |
| UI（side panel / popup / 授权确认） | 长期存储与审计（归 Agent） |

一句话：**壳提供手和眼睛，Agent 提供脑子。**

## 1.1 职责划分 → 见业务架构

壳与 Agent 的职责边界（三条判据、能力归属表、状态归属、责任链、三个易错边界）属**产品级业务架构**，统一维护在：

> [`docs/prd/03-architecture.md`](../../prd/03-architecture.md)

本文只保留**壳自身的技术实现**：部件与进程、MV3 约束、部署形态、通信通道与配置、消息契约、权限最小化、安全。判断"某个能力该放壳还是放 Agent"时，先读业务架构那一份，再回到本文看壳侧怎么实现。

## 2. 部件 × 进程 × 生命期 × 权限

| 部件 | 跑在哪 | 能力 | 生命期 |
|---|---|---|---|
| background（MV3 = Service Worker） | 扩展自己的 renderer | 事件枢纽、`chrome.*` API、维持连接 | **空闲约 30s 被回收**，事件唤醒 |
| content script | 目标页 renderer 的 isolated world | 读写 DOM（与页面 JS 隔离） | 随页面 |
| popup / side panel / options | 扩展 renderer | UI、授权交互 | 打开时 |
| offscreen document | 扩展 renderer（不显示） | SW 没有 DOM 能力时的兜底 | 手动创建/销毁 |
| native messaging host | **本机独立进程**（非浏览器内） | 与扩展 stdio 通信 | 由宿主决定 |

**关键：任何部件都不在 browser process 里。** browser process 只做调度与权限裁决。

## 3. MV3 约束（决定壳能多"薄"）

| 约束 | 影响 | 对策 |
|---|---|---|
| SW 空闲约 30s 终止 | 不能常驻主循环 | 壳无状态；重连由 transport 层负责 |
| WebSocket 在 SW 里可用，有收发会重置空闲计时 | 静默长连接保不住 | 心跳或 `chrome.alarms`（≥30s）保活；或用 offscreen 持有连接 |
| `chrome.alarms` 最小 30s | 无法做秒级定时 | 秒级逻辑放 Agent 侧 |
| `chrome.debugger` 会挂"正在调试此浏览器"横幅 | 用户警觉 + 商店审核敏感 | 优先 content script，debugger 作为兜底 |

## 4. 三种部署形态（Agent 位置是配置项）

| 形态 | Agent 在哪 | 模型在哪 | 什么数据出网 | 延迟 | 离线 |
|---|---|---|---|---|---|
| **A 全本地** | 本机进程 | 本地模型 / 或不出网 | 无 | 最低 | 完整可用 |
| **B 本地 Agent + 云模型** | 本机进程 | 云 API | 仅必要的上下文片段 | 低 | 降级可用（推理不可用） |
| **C 全远程** | 公网云 | 云 | 页面内容 + 任务数据 + 上下文 | 受网络 | 不可用 |
| **D 局域网服务**（当前选择） | **局域网服务器** | 云 API 或本地模型 | 仅推理所需片段（不出局域网即可用本地模型） | 局域网 1–5ms | 局域网内完整；出网推理不可用时降级 |

**要点：把"Agent 在哪"和"模型在哪"分开看。** 大多数隐私诉求不是"模型不能上云"，而是"任务数据与凭证不能上云"——形态 B 正好满足：Agent（含任务库、记忆、审批）在本地，只有推理所需的那一小段上下文出网。

**默认选 B**，A 为离线/敏感场景，C 为多设备与轻客户端场景。

## 4.1 不做中间层（Host）：形态 D 的取舍

**结论：形态 D 下砍掉 Host 是合理的。** 因为"云端"就是局域网服务器，网络边界 ≈ 家庭/办公边界，Host 原本要解决的"拦住不该出网的东西"已经不成立。

原 Host 的六项职责，逐条看落到哪里：

| 原职责 | 砍掉 Host 后 | 结论 |
|---|---|---|
| 传输终结 | 扩展直连 LAN 服务的 `http(s)/ws` 端口 | 无损失 |
| 凭证保管 | **凭证本来就不该上去**：Cookie 在浏览器里，Agent 只需页面语义 | 反而更简单 |
| 审批 | 扩展的 side panel 弹确认（用户正看着浏览器） | 可行，且更顺手 |
| 保活重连 | 扩展用 `chrome.alarms` 心跳；或**按需连接**（空闲断开） | 无损失 |
| 多客户端复用 | LAN 服务天然可被多端访问（桌面/手机/其他机器） | 更好 |
| 协议适配 | 统一走一条 `http/ws` | 简单 |

**代价：三件事必须在别处补上**

1. **认证不能省**。局域网 ≠ 可信网（访客 Wi-Fi、同网段设备、IoT）。做法：服务端首次启动打印 6 位配对码，扩展输入后换长期 token；token 存 `chrome.storage.local`，可撤销。
2. **证书问题要正面解决**。扩展**不允许忽略证书错误**，自签 `wss` 会直接失败。三种落地方式：
   - LAN 内用 `http` + token（简单，风险是同网可嗅探）；
   - 自签证书 + 引导用户先在浏览器访问一次并手动信任；
   - `mkcert` 生成并在系统信任根（一次性配置，之后体验最好）。
3. **服务发现靠人填**。浏览器不能发 mDNS，所以"自动发现"做不到；实际路径是服务端提供一个连接串（`ha+local://192.168.1.10:7801?t=...`）或二维码，用户粘贴/扫描一次即完成配置。

**额外好处**：Agent 在 LAN 服务器上时，**手机、平板、其他电脑同网即可访问**，"多设备"问题顺带解决——这本来是形态 C 才有的能力。

**一条提醒**：提醒不依赖扩展在线。扩展会被 MV3 回收，所以任务提醒必须由服务端走系统通知/IM 推送，不能指望"扩展常驻监听"。

## 5. 通信通道 ↔ 部署形态

| 通道 | 机制 | 对应形态 | 注意 |
|---|---|---|---|
| **Native Messaging** | `chrome.runtime.connectNative`，stdio + 4 字节长度前缀 JSON | A / B | 需安装 host + 注册表项，适合开发者与自用 |
| **localhost HTTP/WS** | `127.0.0.1:PORT` + token | A / B | 必须随机端口 + token，仅绑回环 |
| **wss 直连** | WebSocket over TLS | C | 设备配对 + 令牌 + 可选端到端加密；注意 SW 回收后重连 |

**契约必须与 transport 无关**：同一套消息格式，换部署只换通道。

## 5.1 Gateway 模式与端点配置

Hermes 的做法可以借鉴：它有一个 Gateway 做消息分发，网页端连 Gateway，由 Gateway 路由到 Agent。**我们照搬结构，但要改两处**——Gateway 只做接入不做业务，连接地址由用户配置。

**形态 D 下不需要独立的 Gateway 进程**：局域网服务本身就是接入点（一个 HTTP/WS 端口，天然多客户端），下表的职责合并进该服务即可。

### Gateway 的职责边界

| 做 | 不做 |
|---|---|
| 多客户端接入（扩展 / 桌面 UI / CLI / IM 适配器） | 不持有任务状态（那是 Agent 的事） |
| 认证与设备配对 | 不存页面内容 |
| 按 `thread_id` 路由到 Agent 实例 | 不代替 Agent 做决策 |
| 订阅与事件分发、背压、重连 | 不做跨任务上下文拼装 |

**为什么"不持有业务状态"是硬约束**：一旦 Gateway 存任务，本地优先就破了——换台机器、断网、Gateway 挂了，任务全丢。

### 与 Hermes 的差异

| 维度 | Hermes | 我们 |
|---|---|---|
| 定位 | 消息网关（多 IM ↔ Agent） | **接入层**（多客户端 ↔ Agent） |
| 连接配置 | 写在代码/配置文件里（用户即开发者） | **用户配置**：配对码 / 连接串 / 手动填 |
| 认证 | 本地信任为主 | 远程必须设备配对 + 令牌 |
| 路由 | 按平台会话 | 按 `thread_id` + 多端点 |

### 连接串（统一格式，便于复制粘贴）

```
ha+native://local                                    # Native Messaging
ha+local://127.0.0.1:7801?t=<token>                  # 本地回环
wss://gw.example.com/agent?d=<deviceToken>           # 远程 Gateway
```

一个 URI 涵盖三种 transport，扩展只需一个解析器。

### 配对流程（用户配置的核心体验）

1. 扩展打开 side panel → 显示 6 位**设备码**；
2. 用户在桌面端（或云端控制台）确认该码 → 批准；
3. 服务端下发**长期令牌**，扩展存 `chrome.storage.local`，可随时撤销。

比"用户抄地址 + 抄 token"好一个量级；远程形态下还能顺带绑定设备指纹。

### 端点发现方式的取舍

| 方式 | 依赖 | 体验 |
|---|---|---|
| 配对码 / 二维码 | 一端可达另一端 | **最好**（推荐默认） |
| 粘贴连接串 | 无 | 一般（要复制） |
| mDNS 自动发现（`_harness._tcp`） | **需本地 Host**（浏览器不能发 mDNS） | 局域网内最好 |
| 手动填 host/port/token | 无 | 最差，仅兜底 |

### 多端点与断线

- 扩展可存多个端点（本机 / 公司服务器 / 云），带 `name / uri / token / lastOk / priority`，支持切换与健康检查（`/healthz`）。
- 断线：指数退避 1s → 30s；离线时动作进本地队列（上限 N 条），恢复后按序补发并去重。
- 端点不可达时给明确话术（"桌面端未启动" vs "网络不可达"），别只说"连接失败"。

## 6. 统一消息契约

```jsonc
// 请求
{ "id": "u-1", "method": "page.snapshot", "params": { "tabId": "A1" } }
// 响应
{ "id": "u-1", "result": { "title": "...", "refs": [ ... ] }, "ok": true }
// 事件（无 id）
{ "method": "tab.updated", "params": { "tabId": "A1", "url": "..." } }
// 错误
{ "id": "u-1", "ok": false, "error": { "code": "NO_TAB", "message": "...", "hint": "..." } }
```

对齐 `05-tools` 的工具结果契约：`{ok, data}` / `{ok:false, error{code,message,hint}}`。

## 7. 能力边界：content script 优先

| 需求 | 用什么 | 理由 |
|---|---|---|
| 读文本、找元素、填表单 | `chrome.scripting.executeScript` / content script | 无横幅、无审核风险、够快 |
| 真实点击（避免 `isTrusted:false`） | `chrome.debugger` → CDP `Input` | 部分站点与风控只认真实事件 |
| 截图 / 网络抓包 / 多标签编排 | `chrome.debugger` → CDP | content script 拿不到 |
| 读 Cookie | `chrome.cookies`（按域） | 比 debugger 更窄，权限更可控 |

**原则**：默认 content script；只有"必须真实输入 / 必须看网络"时才升级到 debugger，并在 UI 上明示。

## 8. 计划下推（避免逐步往返）

远程/本地往返一次几十到几百 ms，逐步决策会把任务拖成几十秒。做法：

1. Agent 产出**步骤计划**（`[{op:"goto"},{op:"click",ref:12},{op:"read",selector:"..."}]`）；
2. 扩展到本地**顺序执行**，遇异常或歧义即暂停回报；
3. 批量回报结果 + 页面变化摘要；
4. 支持断点续跑（每步幂等标记）。

这样一次往返能跑完一串动作，延迟与成本都降一个量级。

## 9. 权限最小化清单

| 权限 | 用途 | 最小化方式 |
|---|---|---|
| `activeTab` | 仅当前页 | 优先，避免 `<all_urls>` |
| `scripting` | 注入脚本 | 必选 |
| `host_permissions` | 指定站点 | **按域名白名单**，不做全站 |
| `cookies` | 站点登录态判断 | 按域申请，不读值只判存在 |
| `debugger` | 真实输入/截图/网络 | **可选权限**，用时再申请 |
| `storage` | 本地配置 | 仅配置，不存页面内容 |
| `alarms` | 保活 | 按需 |

## 10. 安全

1. **审批在本地**：危险动作（提交/支付/删除/发消息）由本机 Agent 或扩展 UI 确认，云端无权放行。
2. **凭证不出本机**：远程模式下只传页面摘要，永不传 Cookie / token。
3. **远程需配对**：设备一次性配对码 + 长期令牌 + 可撤销；可选端到端加密。
4. **接管需显式**：默认不碰用户正在浏览的标签页（见 `05-tools/opencli-notes.md` §2.2 接管契约）。
5. **审计**：每个动作记 `{timestamp, method, tabId, result}`，落本地事件流。

## 11. 已定与未定

**已定**

1. **不做中间层 Host**：采用形态 D（Agent 在局域网服务器），扩展直连 LAN 服务；认证、证书、发现三项在扩展与服务端之间解决（§4.1）。
2. **Gateway 定位**：只做接入与路由，**不持有任务状态**；形态 D 下与 LAN 服务合体，不单独起进程（§5.1）。
3. **连接方式**：用户配置为主，优先配对码，兜底连接串与手动填写（§5.1）。
4. **提醒不依赖扩展在线**：由服务端走系统通知 / IM 推送。

**未定**

1. **证书方案**：LAN 内 `http + token` / 自签 + 手动信任 / `mkcert` 入系统信任根 —— 推荐第三条，但要看用户是否愿意一次性配置。
2. 配对码有效期与撤销粒度（设备级 / 端点级 / 会话级）。
3. 多端点切换是否要 UI（还是只按优先级自动选）。
4. 是否需要局域网内"扫码即配"（服务端出码、扩展扫码，避免手输 IP）。
5. `debugger` 权限的申请时机（安装时 vs 首次需要时）。
