## 1. 组件全景

| 组件 | 部署位置 | 职责 | 生命周期 |
|---|---|---|---|
| **桌面壳**（Electron） | 用户电脑 | 工作区 UI + 全局热键 + 系统通知 + **spawn Chrome 并持有 CDP**（页面执行的唯一源头） | 常驻 |
| **Agent 服务** | 本机（v1）/ 局域网服务器 | **控制面**：实例管理（创建 / 启动 / 停止 / 销毁）+ 消息路由 + 任务 / 事件 / 调度 / 审批**策略** | 常驻 |
| **Agent 实例**（worker） | Agent 服务托管，**每 profile 一个进程** | **数据面**：Runtime 主循环 / 上下文装配 / 模型调用 / 记忆检索 / 工具编排 | 随实例 |
| **IM 适配器** | Agent 服务内（飞书 / 钉钉 / 微信插件） | 消息锚定与投递 | 随服务 |
| **浏览器实例** | 用户电脑（桌面壳 spawn） | 页面执行，独立 profile | 按需/常驻 |
| **存储** | 服务本地 **单库** SQLite（带 `profile_id`） | 任务 / 线程事件流 / 提醒 / 审计 / 记忆；**worker 不落盘** | 持久 |
| **模型** | 云 API 或本地模型 | 推理 | 无状态 |

```
┌──────────────────────── 用户电脑 ────────────────────────┐
│  桌面壳（Electron）                                      │
│   ├─ 工作区 UI（看板 / 线程 / 复盘）                       │
│   └─ 浏览器驱动 ──spawn──► Chrome（独立 profile）          │
│                        └──CDP（ws 127.0.0.1:port）──┘    │
└───────────────────────────┬──────────────────────────────┘
                            │ http/ws（v1 回环 / 可选 LAN）
                ┌───────────▼──────────────────────────────┐
                │ Agent 服务（控制面）                       │
                │ 实例管理 / 消息路由 / 任务 / 调度 / IM 适配器│
                │   └─ Agent 实例 × N（每 profile 一个进程）  │
                │        Runtime / 上下文 / 模型 / 工具编排   │
                └──────────────────────────────────────────┘
```

## 2. 三条判据

1. **需要实时页面状态的 → 桌面壳（浏览器驱动）**：DOM、坐标、可见性、网络、标签页。Agent 侧永远滞后一步。
2. **需要跨时间/跨会话的 → Agent**：任务、记忆、审计、调度。壳会被关掉，存不住。
3. **需要"决定"的 → Agent；需要"动手"的 → 壳。** 壳里只允许**机械决策**：重试一次、等一帧、滚动到可见。

| 记忆 / 检索 | ✖ | ✔ | |

| 规划 / LLM | ✖ | ✔ | |
| 步骤计划 | **执行** | **生成** | |
| 审批**策略**（什么算危险） | ✖ | ✔ | |

## 4. 状态归属

| 状态 | 谁持有 | 理由 |
|---|---|---|
| 页面 ref 表 | **壳**（内存，页面一变即失效） | 实时性 |
| 接管的 tab / 租约 | 壳执行、Agent 记账 | 动手在本地，责任在任务 |
| 任务与线程 | **Agent** | 唯一真相 |
| 设备标识 `device_id` | **Agent 服务** | 服务生成并持有；壳不感知（§8.4） |
| 本地共享密钥 | **壳**（读本机文件） | v1 无账号；跨机化改为服务签发 |
| `worker_id` | **Agent 服务** | 壳每次 `ensure` 取得，**不持久化**（避免缓存过期） |
| 待审批请求 | Agent 生成、壳呈现 | |
| 执行中的 step plan | **壳**（支持断点续跑） | 网络断了也要能走完 |

## 5. 一次"提交表单"的责任链

```
用户：把这个表单提交了
Agent  ① 判定需要页面操作 → 生成 plan：fill(ref5) / click(ref9)
       ② 判定是危险动作 → 发起审批
壳     ③ 弹确认 → 用户点「允许」
Agent  ④ 收到批准 → 下发 plan
壳     ⑤ 本地执行：定位 → 滚动 → Input → 等导航
       ⑥ 采集结果快照 → 回传
Agent  ⑦ 更新任务状态、写审计、决定下一步
```

② 与 ③ 必须分开：**"该不该问"是 Agent 的判断，"问不问得到"是壳的界面**。合在一起，换成 IM 通道时审批逻辑就得重写。

## 6. 部署形态与承载

### 6.1 部署形态

| 形态 | Agent 位置 | 说明 |
|---|---|---|
| A 全本地 | 本机进程 | 离线、最私密 |
| B 本地 Agent + 云模型 | 本机进程 | 隐私与能力折中 |
| C 全远程 | 公网云 | 多设备，数据全上云 |
| **D 局域网服务**（当前） | 局域网服务器 | 边界≈内网；免中间层；多设备天然可用 |

### 6.2 承载方式（已定）

| 项 | 决定 |
|---|---|
| 工作区 UI | **桌面壳（Electron）**内，多窗口 / 托盘 / 全局热键都在手 |
| 壳实现载体 | **Electron**：主进程持有 Chrome 子进程与 CDP 连接，渲染进程只做 UI，指令与快照经 IPC 传递 |
| 页面能力 | **桌面壳内 spawn Chrome**（独立 profile）+ 直连 CDP |
| 浏览器扩展 | **不做**：省掉商店审核、`debugger` 权限审查、Chrome 136 对默认 profile 的限制 |
| 中间层 Host | **不做**：CDP 驱动本身就在壳里，没有需要中转的东西 |
| Web 工作区 | 可选形态（同网访问），不是必需 |

**浏览器驱动的实现要点**

```
spawn chrome --user-data-dir=~/.harness/browser/profile --remote-debugging-port=0
  → 读 <profile>/DevToolsActivePort 拿端口与 ws 路径
  → HTTP /json/list 取 target
  → WebSocket 连 browser 端点，Target.setAutoAttach{flatten:true, filter:[{type:'page'}]}
  → 用 Input / Page / Runtime / DOMSnapshot 实现 open / click / type / extract / screenshot
  → 退出时优雅关闭，profile 保留
```

| 要点 | 做法 |
|---|---|
| 端口 | `--remote-debugging-port=0` 随机端口，从 `DevToolsActivePort` 读，不写死 9222 |
| 隔离 | 独立 `--user-data-dir`，不碰用户日常浏览器 |
| 登录态 | 首次在自动化窗口手动登录一次，profile 持久化后长期复用 |
| 连接 | 只绑 `127.0.0.1`；如需更严，用 `--remote-debugging-pipe`（无端口） |
| 回收 | 监听 `Target.targetDestroyed`；闲置 N 分钟关实例或 `target.closeTarget` |

**唯一代价**：登录态要重建一次（用户在自己的浏览器里已登录的站点，不会自动带过来）。可接受——用户在自动化窗口登录一次即长期有效，且这条路径换来的是完全可控、可无头、无需审核。

### 6.3 为什么最终选"自己 spawn"（决策 D17）

候选与取舍：

| 方案 | 登录态 | 干扰用户 | 平台依赖 | 可控性 |
|---|---|---|---|---|
| Chrome 扩展 | 现有登录态，零成本 | 无 | **商店审核 + `debugger` 权限审查 + "正在调试此浏览器"横幅** | 中（受浏览器策略限制） |
| **桌面壳 + 自 spawn**（采纳） | 需重建**一次** | 无（另开窗口） | **无** | 高（无头、并行、确定性回放、UA/指纹可控） |
| 桌面壳 + 复用日常 profile | 有 | **要重启浏览器** | Chrome 136+ 直接禁止默认 profile 开调试 | 中 |
| 纯 Web | 无 | 无 | 无 | 无页面能力 |

**四条决定性理由**

1. **一次性成本 vs 持续性成本**。扩展省下的是"登录一次"这个一次性动作，付出的是永久的平台依赖：审核、权限声明、浏览器版本策略、`debugger` 横幅。自 spawn 反过来——只付一次登录，之后不再受平台摆布。对自用与小团队产品，这笔账很划算。
2. **Chrome 136+ 已经堵死了"零成本复用"**。默认用户目录不允许开启远程调试，想复用日常 profile 只能换 profile 或复制目录——成本比"在自动化窗口登录一次"更高，而且它还是会被版本策略继续收紧。
3. **扩展在 MV3 下本来就不适合当常驻执行端**。Service Worker 空闲即被回收，长连接要保活、状态要同步；而我们的执行模型是"计划下推 + 连续执行"，需要一个**稳定宿主**。桌面壳天然稳定，还能顺手提供全局热键、系统通知、托盘。
4. **链路更短**。扩展方案里页面能力在扩展、UI 在 Web、状态在服务，三者互相中转；自 spawn 后页面能力与 UI 在同一个进程里，只剩"壳 ↔ Agent 服务"一跳，故障面直接少一层。

**代价与边界（写死，避免以后含糊）**

- 登录态需在自动化窗口登录一次；profile 持久化后长期复用。
- **不复制用户日常浏览器的 Cookie**——合规红线，不因为"方便"而破。
- 不追求"接管用户正在浏览的页面"。需要这个能力时，再把扩展作为**可选第二后端**评估，而不是现在预留半套架构。

**反悔条件（预先约定，避免拍脑袋改）**

| # | 条件 | 为什么它能推翻方案 |
|---|---|---|
| 1 | 关键站点**连"人工登录一次"都无法完成或维持**（U 盾 / 客户端证书、每次强制重绑设备） | 登录态建不起来，方案前提就没了 |
| 2 | 用户**拒绝使用独立的自动化浏览器窗口**，且这类需求占多数任务 | 那个窗口就是执行载体，拒绝等于否掉载体 |
| 3 | 站点对 CDP 的检测严到无法完成基本操作（滑块 / 指纹频繁拦截），人工登录后依旧 | 不可用 |

**注意**：「能不能接管用户当前页面」**不在**上表里。因为它不是"需求多到一定程度就改方案"的问题，而是**当前形态下根本做不到**，也不该被当成可承诺的能力。见 §6.5。

### 6.4 登录处理：只停不登（红线，D18）

**规则：Agent 永不代用户登录。**遇到登录墙就停下来，把控制权交回人。

三条理由：① 代登录必然要碰账号密码与验证码，等于把凭据喂给模型；② 站点风控对"人类手动登录"宽容得多，代登录几乎必被拦；③ 登录失败的责任边界无法界定。

**检测（任一信号命中即暂停）**

| 信号 | 权重 |
|---|---|
| 页面出现 `input[type=password]` | 最强 |
| URL / 标题命中 `login` / `signin` / `auth` / `sso` / `登录` | 强 |
| HTTP 401 / 403 且发生跳转 | 强 |
| 出现验证码容器（`captcha` / `slider` / `geetest`） | 直接停 |
| 预期元素缺失 + 页面出现"请先登录"文案 | 兜底 |

**流程**

```
plan 执行到某步 → 检测到登录墙
  → 暂停 plan（已完成步骤保留，不重跑）
  → 确保窗口可见（无头则切有头）并置前
  → 壳内提示：「请在窗口中完成 登录（站点名），完成后点继续」
  → 等待：URL 变化 / 密码框消失 / 用户菜单出现 / 用户点「继续」
  → 超时 10 分钟 → 任务转 paused，备注「等待人工登录」
  → 恢复后从断点续跑（step 幂等）
```

**边界（写死）**

- **不保存、不填写账号密码**，不勾"记住我"。
- **不处理验证码**（滑块 / 点选 / 短信），不尝试任何绕过。
- **不做登录态搬运**（复制用户浏览器 Cookie / 导出 storageState 用于他人环境）。
- **无头模式不执行需要登录的操作**：要么切有头，要么直接失败并说明原因。
- **IM 触发的任务遇到登录墙**：不能弹窗 → 转 `paused` + 推 IM「需要你在电脑上登录 X」。

**这条规则顺手把风控问题降级了**：用户手动登录在站点看来就是正常人类行为，通过率远高于任何自动化流程。于是 §6.3 里"新设备验证"这个技术难题，本质变成了一次用户交互。

### 6.5 能力边界：不能接管你正在用的浏览器（必须明说）

**事实**：Agent 不能操作用户当前正在使用的那个浏览器标签页。

技术原因有三条，都是 Chrome 的安全设计：

1. CDP 端点只能在浏览器**启动时**开启，无法对已经运行的实例追加；
2. Chrome 136+ **禁止在默认用户目录上开启远程调试**——其初衷正是防止恶意程序通过 CDP 窃取 Cookie；
3. 想接管现有页面只有一条路：装扩展走内部 `chrome.debugger`，而我们已决定不做扩展（D17）。

**产品必须主动说清三件事**（写进首次引导、帮助页、错误提示，而不是等用户问）

| 要说清的 | 话术 |
|---|---|
| 不碰你的浏览器 | "AI 在一个独立浏览器窗口里工作，不会动你正在用的浏览器。" |
| 需要登录一次 | "第一次用某个网站时，需要你在那个窗口里登录一次，之后会记住。" |
| 接着你手头的操作：做不到 | "如果你已经在自己浏览器里操作到一半，AI 无法接手继续——请把链接或内容发给它。" |

**为什么这是保护而不是缺陷**：Chrome 限制 CDP 的本意就是防止"本地程序悄悄接管浏览器偷 Cookie"。我们遵守它，等于不给这类攻击留入口。这个说法对用户是加分的，不要藏。

**对外不承诺**（避免过度承诺后翻车）

- ❌ "能在你当前页面上操作"
- ❌ "自动继承你已登录的状态"
- ❌ "能处理需要 U 盾 / 客户端证书的站点"

**遇到用户提问时的标准回答**：不是"我们不支持"，而是"Chrome 不允许正在运行的浏览器被外部接管，这是为了防止 Cookie 被窃取；所以 AI 用自己的窗口工作，你登录一次就行"。

## 7. 三个易错边界

1. **壳里别做业务决策**：一旦壳开始判断"该不该点"，就会长出第二套逻辑，永远改不齐。
2. **别把 DOM 原文整体上送**：壳先裁剪成"可操作元素 + 文本片段"，否则 token 爆炸、隐私失控。
3. **Agent 里别缓存坐标/ref**：页面一变全部失效，ref 只能保证"本次计划内有效"。

## 8. 壳 ↔ Agent 实例：v1 本地实例模型（D19）

### 8.1 为什么仍拆两个角色

v1 取消远程注册登录，定位**本地部署**（默认 `127.0.0.1`）。仍拆「壳 + Agent 实例」两个进程，理由不是安全隔离，而是**生命周期不同**：壳是 UI，随用户开关与版本迭代频繁重启；任务执行需要稳定宿主。拆开后壳可以完全无状态，重连即恢复。

设计上按**可跨机**约束（不共享内存 / 文件句柄 / 本地 socket 路径，只走 HTTP/WS），部署上默认同机。将来切 LAN 只改 bind 地址与凭据分发，不动协议与代码。

### 8.2 三方职责

| | 壳 | Agent 实例（worker） | Agent 服务（控制面） |
|---|---|---|---|
| 职责 | UI / 热键 / 通知 / spawn 并驱动 Chrome | Runtime 主循环、上下文装配、模型调用、记忆检索、工具编排 | 实例管理（创建 / 启动 / 停止 / 销毁）、消息路由 |
| 身份 | **无** | `worker_id`（服务分配） | 持有 `device_id` 与实例注册表 |
| 状态 | 页面 ref 表、CDP 连接、共享密钥 | 会话内存态（**不落盘**） | 单库：任务 / 线程事件流 / 提醒 / 审计 / 记忆；调度、审批策略、配额 |

**切分判据**：需要跨实例一致性的留在服务；只有局部运行态的放进 worker。实例是"一个 worker"，不是"一个小号完整产品"——否则多实例会出现记忆分裂与定时任务重复触发。

**持久层单库、单写入者**：任务、线程事件流、提醒、审计、记忆同在一份 SQLite（带 `profile_id` 列），库随服务；worker 只持有内存运行态，会话事件经服务写入。理由：到点提醒、`paused` 回访、日终复盘、全量导出都是跨任务的时间维度查询，单库一条 SQL 即可；分库会让这些逻辑退化成"遍历所有库"。串行执行 + 单写入者，SQLite 的单写者限制不构成瓶颈。反悔条件见 §8.7。

**页面执行的唯一源头是壳**：spawn Chrome、持有 CDP 连接、把 `ref` 定位成坐标、执行点击与输入，全部发生在壳内。Agent 只下发**语义指令**（`click ref=12`），不下发坐标、不持有页面状态、不具备 CDP 能力。这是 D17 的直接推论——任何"让 worker 直连浏览器"的改动都等于推翻 D17，需走反悔条件（§6.3）。

### 8.3 `ensure` 语义（壳唯一的入口动作）

壳启动只发一条 `POST /instances:ensure { profile }`，服务端在**一个锁内原子完成**「查 → 启动 → 登记」：

| 服务端现状 | 动作 | 返回 |
|---|---|---|
| 该 profile 的 worker 运行中 | 复用，不重启 | `running` + `worker_id` |
| 存在但已停止 | `resume`（加载磁盘会话） | `running` + `worker_id` |
| 不存在 | `create` + `start` | `running` + `worker_id` |
| 已被 `destroy` | 报错，不自动重建 | `destroyed` |

壳**不持有** `worker_id`：不缓存、不持久化，每次连接重新 `ensure`。多一次 1ms 的请求，换掉"缓存指向已销毁实例"这一整类故障。

失败必须可区分，不要统一 500：服务未启动（连接被拒）/ profile 不存在 / 配额不足 / worker 崩溃重启中——四者的壳侧提示完全不同。

### 8.4 身份与认证（无账号）

- **`device_id`**：服务首次启动生成，存 `~/.harness/device.json`（用户级机器标识，**跨 profile 共享**、**不进 SQLite**、不进 git）。UUIDv7，与硬件解耦。
- **服务是唯一签发方**：壳不生成、不读该文件，只从 `ensure` 响应里拿到（可以不存）。理由：壳升级/重装频繁，身份挂在生命周期更长的一侧。
- **`mac_hints` / `hostname_hint`**：仅作管理页展示与"疑似同一台"提示，**不参与匹配**。MAC 不稳定的场景（多网卡、虚拟网卡、随机硬件地址）不能用来做身份。
- **通道凭据**：`~/.harness/local.secret`（权限 0600），服务首次启动生成，壳读同一文件带 `Authorization`。默认只绑 `127.0.0.1`；切 LAN 只改 bind 与密钥分发。
- **服务必须单实例化**（`~/.harness/harness.lock`）：两个进程各自生成 `device_id` 会让注册表分叉。

### 8.5 写死的四条约束

1. **`ensure` 幂等**：同一 `(device_id, profile)` 重复请求只返回已有 worker，不新建。壳网络抖动重试是必然事件。
2. **`stop` 与 `destroy` 分离**：`stop` 保留磁盘会话、可 `resume`；`destroy` 删数据。无账号体系时误 `destroy` 等于永久丢失。
3. **父进程托管（v1）**：服务 spawn worker，经 stdio JSON-RPC 通信，父进程退出即断连、天然无孤儿。服务重启会中断 worker，但会话已落盘，壳 `ensure` 自动重建并 `resume`。**detach（独立进程 + named pipe + supervisor 重连，使升级不打断任务）列为 v1.1**，详见 `../designs/10-control-plane/README.md`。
4. **失联回收走租约**：壳 60s 无心跳 → 标 `lost` → 保留磁盘、停进程。否则崩溃一次就留一堆僵尸实例。

### 8.6 多客户端与接管

多连接**只读订阅、写入串行**：所有连接都能收事件流；只有持有当前 turn 的客户端能发用户消息；`interrupt` 需显式请求，**不默认"新连接即抢占"**。否则用户重开一个窗口就把正在跑的任务打断。

### 8.7 反悔条件

| 条件 | 改法 |
|---|---|
| 需要壳脱离服务独立运行 | 改为壳生成 `client_key` → 服务签发 `device_id` |
| 需要多设备共用一个服务（LAN） | 补首次连接的凭据签发，壳开始持久化本地凭据 |
| 需要多用户 / 多租户 | 见 `../designs/00-overview/design.md` §11 待定项 |
| 需要服务升级不打断运行中任务 | 切 detach：独立进程 + named pipe + supervisor 重连（v1.1） |
| 需要 profile 级物理隔离 / 独立备份迁移（多人共用一台机、客户数据交付） | 按 profile 竖切分库，同时 worker 改为自持久化；若只是单库体积过大，优先用 SQLite `ATTACH` 拆"元数据单库 + 内容分库"，不按 profile 竖切 |
