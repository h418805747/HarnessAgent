# 08 Security 安全

> 状态：草案 v0.2（依据"安全不可被 Agent 卸载"评审修订）
> 对应概要设计 §2.3、§5.4

## 0. 定位：信任根，而非普通插件

上一版把 Security 简单列为"可替换插件"，存在严重缺陷。必须区分三个被混为一谈的概念：

| 概念 | 含义 | Security 是否适用 |
|---|---|---|
| **可替换 Replaceable** | 实现可换，接口保持不变 | ✅ 是（策略引擎 / 沙箱后端 / 密钥后端可换） |
| **可卸载 Removable** | 运行期可整体移除且系统仍能工作 | ❌ 否（移除即等于关闭安全） |
| **可被 Agent 卸载 Agent-removable** | 模型可通过工具调用触发移除 | ❌ **绝对禁止** |

**结论：Security 是内核信任根（TCB）常驻组件。它可以"被换实现"，不可以"缺席"，更不可以"由 Agent 触发移除"。**

> "Everything is a plugin" 适用于**能力（capability）**，不适用于**信任根（trust root）**。
> 类比操作系统：内核调度器、安全模块不能被用户态进程卸载；但防火墙实现可以由 root 在**启动时**替换。

## 1. 威胁模型

| 编号 | 威胁 | 场景 |
|---|---|---|
| T1 | **提示注入卸载安全** | 网页/文件/工具输出等外部内容诱导模型调用"卸载插件""关闭安全" |
| T2 | **策略篡改** | 模型或第三方插件修改安全策略、白名单、`always-allow` 记录 |
| T3 | **审批伪造/绕过** | 绕过审批链直接执行敏感操作 |
| T4 | **密钥窃取** | 通过工具读取 `.env`、环境变量、凭证 |
| T5 | **审计破坏** | 删除/篡改审计记录以掩盖行为 |
| T6 | **插件投毒** | 恶意插件在挂载时注册高权限能力或覆盖安全组件 |

T1 是本模块设计的核心驱动威胁。

## 2. 分层结构（三层，权限递减）

```
┌── L1 Security Core（内核 TCB：常驻、不可卸载、不暴露为工具）──────────────┐
│  Policy Decision Point (PDP)      │  Policy Enforcement Point (PEP)      │
│  插件生命周期授权 Gate             │  配置变更授权 Gate                    │
│  保护清单 Protected Set 校验       │  审计锚点（append-only）              │
│  任何异常/超时 → fail-closed       │                                       │
└────────────────────────────────────┬──────────────────────────────────────┘
                                     │ 只通过接口调用（单向依赖）
┌── L2 Security Providers（插件：可替换，但不可缺）─────────────────────────┐
│  策略引擎 IPolicyEngine │ 沙箱后端 │ 密钥后端 ISecretStore │ 审计 Sink │ 检测器 │
│  规则：缺失/加载失败 → 拒绝；绝不 → 放行（fail-closed）                    │
└────────────────────────────────────┬──────────────────────────────────────┘
┌── L3 Admin Operations（带外，需人类显式授权）─────────────────────────────┐
│  修改策略 / 挂载卸载插件 / 关闭安全                                        │
│  仅控制面（CLI、配置文件、supervisor）可发起                               │
│  需人类确认 + 重启或监督模式；永不注册为模型可调用的工具                    │
└────────────────────────────────────────────────────────────────────────────┘
```

## 3. 关键设计点

### 3.1 控制面 / 数据面分离（最核心）
- **数据面**：模型运行于此，只能**请求**动作（工具调用）。
- **控制面**：插件挂载/卸载、策略修改、配置变更、密钥读写。
- **规则**：数据面**永远无法**驱动控制面。模型不能挂载/卸载任何插件，也不能修改安全策略。

### 3.2 结构性隔离优先于策略判定
- 最强防护是"**模型根本没有这个工具**"。
- 插件管理、安全开关、策略编辑、密钥管理**一律不注册为工具**，因此通过提示注入也无可调用之物。
- 策略判定（L1）只是第二道防线，不是唯一防线。

### 3.3 授权与执行分离
- 即便 Creator 模式需要插件管理能力，也必须：`ISecurityCore.authorize_control_plane()` 判定 + **人类审批** + 仅允许操作**非 TCB 插件** + 全程审计。
- 模型只能"请求"，人类才能"授权"。

### 3.4 TCB 冻结与保护清单
- bootstrap 完成后，**TCB 组件集合运行期不可变**；任何变更需重启。
- **保护清单（Protected Set）**：Kernel、Security Core、Plugin Host 权威、Config 权威、Audit。其 `protected=true`，卸载请求**直接拒绝**（不进入审批，直接 deny）。

### 3.5 Fail-closed
- 安全组件不可用、异常、超时、策略为空 → **一律拒绝**，绝不默认放行。
- Security 的"拒绝"决策**不依赖任何普通插件**（依赖循环是漏洞来源）。

### 3.6 风险分级与审批强度

| 风险级 | 示例 | 默认策略 |
|---|---|---|
| L0 只读 | 读文件、搜索 | 允许（可配置为记录） |
| L1 可逆写 | 写文件、创建目录 | 记录 + 可配置审批 |
| L2 破坏性/外发 | 删除、网络请求、执行命令 | 审批 |
| L3 控制面 | 挂载/卸载插件、改策略、改配置、读写密钥 | **强制人类审批，且不可 always-allow** |

### 3.7 always-allow 的边界
- 仅对 L0/L1/L2 生效，作用域受限（工具级 / 参数模式级 / 会话级）。
- **L3 永不可 always-allow**，每次都必须显式人类确认。

### 3.8 用户的自由（不牺牲安全）
- 用户是 root，**有权**关闭安全，但必须是：
  - **带外**：编辑配置文件 / CLI 显式操作；
  - **需重启**：不接受运行期热切换；
  - **有警告**：明确提示风险；
  - **留痕**：标记为 `unsafe mode` 并写入审计。
- 即"用户可以关，但不能在对话里被一句话关掉"。

### 3.9 审计与完整性
- 所有安全判定结果 append-only 写入事件流，可回放。
- 关键决策尽量 tamper-evident（哈希链，可选强度）。
- 插件清单校验；可选签名；标记来源可信度。

## 4. 对提示注入的纵深防护

| 层面 | 措施 |
|---|---|
| 能力面 | 控制面操作不注册为工具（结构性，最强） |
| 授权面 | 即使请求抵达 L1，也被判定为"需人类授权" |
| 审批面 | L3 强制人类确认，不可 always-allow |
| 数据面 | 工具输出/外部内容标记为**不可信输入**，不得作为控制指令 |
| 完整性 | TCB 冻结 + 保护清单 + 变更需重启 |
| 检测面 | 注入检测器（可选），仅作纵深，不设为唯一防线 |
| 兜底 | Fail-closed + 审计告警 |

## 5. 范围

**做**：
- 权限策略模型、审批流、风险分级
- 控制面授权 Gate（插件生命周期、配置变更）
- 沙箱隔离策略、密钥管理、审计
- 输入/输出安全过滤（提示注入防护、脱敏）

**不做**：
- 不实现具体工具执行（提供判定，执行在 Tools）
- 不做企业级 RBAC/SSO（首版）

## 6. 对外接口（修订）

```python
# ---- L1 内核 TCB：常驻，不可卸载 ----
ISecurityCore
    check(action, ctx) -> Decision{allow|deny|ask, risk, reason}
    authorize_control_plane(op, ctx) -> Decision     # 仅控制面可调用；L3 强制人类
    is_protected(name) -> bool                       # 保护清单查询
IApproval
    request(action, ctx) -> Approval                 # L3 不可 always-allow
ISandboxPolicy
    resolve_backend(action, risk) -> ExecutionBackend
ISecretStore
    get(key) / set(key)                              # 独立于 config，不落事件流
IAudit
    record(decision, action, ctx) -> Event           # append-only

# ---- L2 可替换插件接口（内核只依赖接口，fail-closed）----
IPolicyEngine   # evaluate(action, ctx) -> Decision
IDetector       # inspect(content) -> Risk
```

**明确约束**：
- `unmount()` **不出现在任何安全接口上**；插件卸载走 `IPluginHost`，且**必须**先经 `ISecurityCore.authorize_control_plane()` + 人类审批。
- Security Core 的依赖方向是**单向向内**：它不依赖普通插件即可独立做出"拒绝"决策。

---

## 7. 依赖

- 内核（作为 TCB 常驻组件）
- Interface（审批交互 UI）
- Tools（隔离执行）

**禁止**：Security 不得依赖任何普通插件才能运行（否则形成绕过路径）。

## 8. 待定问题

- 保护清单是否允许用户扩展（例如保护自研插件）——倾向允许，但扩展操作本身是 L3。
- 审计 tamper-evident 的实现强度（哈希链 vs 外部不可变存储）。
- 是否需要独立"安全监督进程"（supervisor），与主进程隔离以防同进程内存篡改。
- `unsafe mode` 的边界定义与提示强度。
- 是否支持对 L3 操作的双人审批（当前为单用户场景，暂不需要）。
