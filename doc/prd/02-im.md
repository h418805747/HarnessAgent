## 1. 本域负责什么

| 负责 | 不负责 |
|---|---|
| 各平台接入、能力差异、消息模板 | 任务状态合法性（→ 01-task §3 矩阵） |
| **消息归属**（这条消息属于哪条任务） | 该不该提醒、提醒说什么（→ 01-task §5） |
| **交互载体**（按钮/下拉/编号/H5）与降级链 | run 的调度与预算（→ 02-runtime） |
| 出站投递、两段式、深度链接 | 看板与工作区 UI（→ 09-interface） |
| IM 侧动作白名单、安全、去重、限流 | 数据出本机的策略（→ 总纲 D4/D15） |

**一句话定位**：IM 是任务的**远程入口**，不是第二套产品。它只做三件事——**收指令、给摘要、让人拍板**。

---

## 2. 三条设计原则

1. **通道无关**：IM 与桌面写的是**同一条** `thread_id`。桌面切到该任务，能看到微信里说的那句话；不存在"IM 会话"与"桌面会话"两套历史。
2. **不让用户做锚定**：我们发出的每条推送自带 `task_id` 与按钮，用户"点"即可，不产生需要解析的自由文本。自由文本才是要兜底的少数情况。
3. **重活回桌面**：长文、diff、产物全文、配置一律不在 IM 里做，给摘要 + deep link（`ha://task/<id>`）。

## 3. 平台能力矩阵

| 平台 | 双工 | 可用交互载体 | 关键限制 |
|---|---|---|---|
| **飞书** | 完整 | A 按钮卡片 + B 下拉/表单（话题/线程可做天然分栏） | 频率限制；需自建应用 |
| **钉钉** | 完整 | A 按钮卡片（互动卡片可带下拉） | 单卡按钮数量有限 |
| **企业微信** | 中 | A 模板卡片按钮 | 被动回复窗口短 → 长任务两段式 |
| **微信服务号** | 半双工 | C 编号回执 + D H5 | 无卡片；需企业主体与认证 |
| **微信个人号（iLink）** | 双工（第三方） | C 编号回执 + D H5 | 无按钮/卡片；消息长度受限；合规风险 |

## 4. 微信：分级与合规底线

### 4.1 四种形态能不能用

| 形态 | 能否双向 | 合规性 | 结论 |
|---|---|---|---|
| 个人微信 · 自建协议/hook（Wechaty、padlocal、注入） | ✓ | 违反用户协议，封号 | **产品不做** |
| 个人微信 · **iLink Bot API 扫码登录** | ✓ 扫码即通 | **第三方托管**：二维码由其下发，`account_id/token/base_url` 与消息内容均经其服务；非官方通道 | **自用可选插件**，不进产品主链路 |
| 企业微信（含「微信客服」） | ✓ | 官方 API | 有公司权限时**正路** |
| 微信服务号 | 半双工（48h 客服窗口 + 模板消息） | 官方 | 长期正路，个人申请不了 |

### 4.2 能力分级（也是交付顺序）

**先校正术语**（早期版本用"半双工"不准确，容易和通信里的"轮流单向"混淆）：

| 术语 | 含义 | 谁具备 |
|---|---|---|
| **全双工** | 在同一个通道里能来回：你发消息 → 助手在同一处回你 | 飞书 / 钉钉 / 企微 / iLink |
| **单向回填（只进不出）** | 你能把话送进来，但助手**不能在微信里回你**，回应只能落到系统通知 | 个人微信（M1 的 L2） |
| **单向推送（只出不进）** | 只能收到提醒，想说话没地方说 | 个人微信（M1 的 L1） |

| 级别 | 体验 | 实现 | 何时 |
|---|---|---|---|
| **L1 单向推送** | 手机收到提醒（短码 + 按钮文案） | 桌面通知 → 系统镜像（Phone Link / 小米妙享 / 华为多屏协同） | M1 |
| **L2 单向回填** | 转发/复制一句话即落到任务，但**微信里没有回复**；回应走 L1 通知 | 桌面捕获（文件传输助手 + 剪贴板/拖拽）+ §5 归属 | M1 |
| **L3 全双工（合规）** | 微信里引用回复、点按钮、多轮 | 企微「微信客服」或认证服务号 | 有主体资质后 |
| **L3′ 全双工（自用）** | 同上，但只在个人号 | iLink 扫码登录（第三方插件） | 可选，自装 |

### 4.3 关于 L3′（iLink）

**iLink 是什么**：一个第三方的"微信机器人"云服务。它替开发者完成了两件最难的事——逆向/维护微信协议、托管登录态——对外只暴露一组 API。你扫码确认后，它替你收发消息；开发者拿到 `account_id` / `token` / `base_url` 就能像调官方接口一样调个人微信。

**"插件"指什么**：不是微信的插件，是**我们产品的一个独立适配器进程**，放在 `~/.harness/plugins/im-ilink/`，实现 `IImAdapter`（`send` / `onCallback` / `capabilities`），用长连接接 iLink。装它 = 多一条通道；卸它 = 微信侧退回 L1/L2，飞书钉钉不受影响。

Hermes 的做法可直接复用：`hermes gateway setup` → 选 Weixin → 向 iLink Bot API 请求二维码 → 手机扫码确认 → 凭证存 `~/.hermes/weixin/accounts/` → 起网关收发。

**但产品里必须写死四条**：

1. **数据出本机**：登录态与消息内容经第三方，与"本地优先"冲突，接入时显式告知（总纲 D4 需一并计入）。
2. **默认不装**：只作 `~/.harness/plugins` 里的自装插件，**不进安装包、不进默认配置**。
3. **可拔**：IM Gateway 以适配器形式接入，拔掉不影响飞书/钉钉/通知链路。
4. **风险自负**：封号与接口变更不属产品缺陷，不做兼容承诺。

> 结论：**"在微信上按任务沟通"在产品上必须支持，但个人微信上无法合规实现。** M1 交付 L1 + L2，形态是"**能进不能回**"：你在微信（或桌面剪贴板）里说一句，任务状态会变，但助手不会在微信里回你，回应落在系统通知。想在微信里真正来回对话，只有 L3（要资质）或 L3′（要装第三方插件、接受数据出本机）。

## 5. 消息归属（点选优先）

### 5.1 前置：推送即锚定

主动推送天然绑定 `task_id`，附带 2–4 个内联动作。用户点击 → 直接携带 `task_id` 回到 `transition()`，**零归属成本**。

需要解析归属的只有一种情况：**用户主动发了一句没有锚点的话**。

### 5.2 五层短路

| 层 | 依据 | 命中条件 | 可靠性 |
|---|---|---|---|
| **L0 点选** | 按钮 / 下拉 / 编号回执 | 推送自带 `task_id`；或上一轮已给候选列表 | 最高，零歧义 |
| **L1 引用** | `quoted_msg_id` | 用户引用（长按回复）助手某条消息 | 高（`msg_id → task_id` 映射） |
| **L2 短码** | 文本含 `#T-XXXX` | 用户显式指定 | 高 |
| **L3 粘性** | 会话最近活跃任务 | 同会话 30 分钟内只跟一个任务交互 | 中 |
| **L4 语义** | AI 判定 | 候选唯一且置信度 ≥ 0.8 | 中 |

- **L4 不确定 → 直接给候选点选**：回 2–3 个候选任务（按钮；不支持按钮的平台降级为"回复 1/2/3"）。把"再问一轮"变成"点一次"。
- 候选都不中（用户说"都不是"）→ 问"要建成新任务吗？"；不答则进快速问答（不落产物）。
- 归属结果与依据落事件：`im.routed{task_id, layer, confidence}`，用于算准确率。
- **不猜**是硬要求：归属错了会把 A 客户的话写进 B 任务，比不归属更糟。

## 6. 交互载体与降级链

**能不能点选是平台能力问题，不是产品取舍。** 抽象 4 种载体：

| 载体 | 体验 | 需要的能力 |
|---|---|---|
| **A 按钮卡片** | 点一下即完成 | 消息卡片 + 回调 |
| **B 下拉/表单** | 选任务 + 选状态，一次提交 | 互动卡片 |
| **C 编号回执** | 回"1 / 2 / 3" | 纯文本即可 |
| **D H5 落地页** | 点链接到浏览器点选 | 通知带 URL（一次性 token） |

**降级链（写死）**：`A 按钮 → B 下拉 → C 编号 → D H5`。

同一动作在所有平台必须能完成，只是点的次数不同。微信个人号只剩 C 和 D，所以**编号回执是微信侧的主力交互**——"1 完成 / 2 搁置 / 3 改期"。

## 7. 动作白名单

| 允许 | 禁止 |
|---|---|
| 查看任务摘要 / 今天 Top3 / 谁在等我 | 修改配置、装卸插件、改权限（**控制面**） |
| 状态流转：完成 / 搁置 / 转等待 / 继续 / 改期 | 删除任务、批量操作、导出全量数据 |
| 审批：点按钮放行 / 拒绝 | 对外发消息（邮件 / 催办）未点按钮确认 |
| 让 AI 在任务内起草（结果回摘要 + deep link） | 查看长文、diff、产物全文 |

白名单之外一律回："请到桌面端操作。"白名单内的**状态流转合法性**仍由 01-task 的矩阵裁决（越界返回 `IllegalTransition`）。

## 8. 安全（IM 等于远程控制台）

1. **身份**：IM 账号必须与桌面端绑定（一次性绑定码）；未绑定的会话只回"请先在桌面端绑定"，不执行任何指令。
2. **审批**：必须点按钮，**不接受**自然语言"同意/可以/发吧"（防误发与被冒充）。
3. **去重**：`platform + msg_id` 幂等，防平台重投导致重复执行。
4. **预算**：IM 会话每日 token 上限，超限降级为只读（可查，不可触发 run）。
5. **隔离**：IM 侧只能触达任务域接口，不能触达控制面（插件、配置、策略）。
6. **留痕**：所有指令与结果写事件流，标注 `channel=im` 与原始消息 ID。

## 9. 出站形态

### 9.1 两段式（通用兜底）

```
用户：帮我起草催办
助手：已开始（#T-7F3），预计 1 分钟        ← 回执 ≤ 2s
…（后台 run）
助手：草稿好了 → 摘要 3 行 + [发出去] [改] [去桌面看]   ← 完成后推
```

IM **不做流式输出**；超 5 分钟给一次进度提示。

### 9.2 模板要素

每条出站消息必须含：任务标题、短码 `#T-XXXX`、状态徽标、时间语义（"3 小时后"而非绝对时间）、1–2 个动作、可选 deep link。

### 9.3 限制处理

| 限制 | 处理 |
|---|---|
| 消息长度（微信尤甚） | 分片 + 摘要优先；全文走 deep link |
| 频率限制 | 合并同类，单日上限同 01-task §5.3 |
| 被动回复窗口短（企微） | 一律两段式，长任务不占用窗口 |
| 无回调能力（服务号模板） | 降级为 D（H5），动作在网页完成 |

## 10. IM 域指标

| 指标 | 目标 |
|---|---|
| 消息任务归属准确率 | ≥ 90% |
| 归属失败率（落到候选点选） | ≤ 10% |
| IM 指令响应时延（回执） | ≤ 2s |
| 提醒触达率 | ≥ 95% |
| 提醒响应率（1h 内有内联动作） | ≥ 45% |
| IM 参与闭环任务占比 | ≥ 20% |
| 白名单外动作执行 | **0** |
| 未绑定账号执行指令 | **0** |
| 重复执行（同一 `msg_id`） | **0** |

## 11. 对接契约

```
// 出站：由 01-task 的提醒语义驱动
IReminderRenderer
  render(reminder, capabilities) -> OutboundMessage
  # capabilities: {buttons, dropdown, numbered, h5} 由适配器声明

// 入站：解析后统一交给任务域
IImIngress
  onMessage(platform, raw) -> InboundIntent
  # InboundIntent: {taskId?, action?, text?, confidence, layer}
  # 一律经 ITaskService.transition()，不自带状态判断

// 适配器接口（L3′ 也走这个，便于拔插）
IImAdapter
  capabilities() -> Capabilities
  send(msg) / onCallback(payload)
  verify() -> {ok, accountId}
```

**关键约束**：IM 适配器**不写库、不改状态**，只做"翻译 + 投递 + 回调"。所有状态变更回落到任务域，保证桌面与 IM 行为完全一致。
